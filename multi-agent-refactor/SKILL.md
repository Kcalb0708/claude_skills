# 多 Agent 协同开发 — 标准工作流

当用户要求进行多文件开发、项目搭建、功能开发、代码重构，或提到"多agent""并行""协同""拆任务"时，按本流程执行。

**适用场景**：
- 🆕 **从 0 到 1 新建项目**：搭建目录结构、多模块并行开发
- ✨ **新功能开发**：跨多文件的新功能实现
- 🔧 **代码重构**：已有代码的结构调整和优化
- 📝 **批量修改**：配置迁移、API 替换、依赖升级等

---

## 总览：五个阶段

```
阶段一  需求分析与方案设计 → 生成【总计划.md】
阶段二  任务拆分 → 按强相关性分组 → 生成 N 组【分支任务清单.md】+ 创建 N 个分支
阶段三  并行执行 → 每个 Agent 在自己的分支独立编码 → commit
阶段四  逐分支审查 → Codex 审查每个分支 → 如需修复 → fix/ 分支
阶段五  合并 + 集成审查 → integrate/ 分支 → Codex 审查合并结果 → 如需修复 → fix/ 分支
```

---

## 阶段一：需求分析与方案设计 → 总计划.md

在任何 Agent 动手之前，**人先把所有决策做完**。Agent 擅长精确执行，不擅长在模糊中探索。

### 不同场景的分析侧重

| 场景 | 分析重点 |
|------|---------|
| **从 0 到 1** | 目录结构设计、模块划分、接口约定、数据流设计 |
| **新功能** | 现有代码阅读、插入点定位、接口设计、影响范围评估 |
| **重构** | 调用链分析、改动/不动范围、函数签名变更、向后兼容 |
| **批量修改** | 全量扫描、替换规则、边界情况、回归验证 |

### 执行步骤

1. **理解需求** — 明确要做什么、做成什么样、有什么约束
2. **分析现状** — 读代码 / 画架构图 / 画调用链（新项目则设计架构）
3. **确定范围** — 要创建/修改哪些文件，**不能碰**哪些文件
4. **做技术决策** — 目录结构、函数签名、数据结构、错误处理等全部确认
5. **识别风险** — 可能出错的地方和应对方案

### 产出模板：总计划.md

**重构/修改场景**：

```markdown

| yyy.js | 微调 | -3/+1 行 |
| 其他 N 个文件 | 不动 | 0 |

| 文件 | 不动原因 |
|------|---------|

## 技术决策记录
| 决策 | 结论 | 理由 |
|------|------|------|

（分支全景图）
```

```markdown
| 文件 | 内容 | 被谁依赖 |

| 决策 | 结论 | 理由 |
|------|------|------|
```

### 关键原则

- **"不动清单"比"改动清单"更重要**（重构场景）— 防止 Agent 越界
- **"接口约定"比"内部实现"更重要**（新建场景）— 让各分支并行不冲突
- **决策全部前置** — 总计划中不应有"待定"项
- **架构图/调用链必须画** — 不画就拆任务 = 盲拆

## 阶段二：任务拆分 → 按强相关性分 N 组

### 分组原则：强相关性合并，弱相关性拆分

核心思路：**把改动同一个文件、或存在强数据依赖的任务归为一组，把改动不同文件、仅通过接口关联的任务拆到不同组。**

#### 第一步：识别强相关任务（必须合并为一组）

以下情况说明两个任务**强相关**，必须放在同一个分支、由同一个 Agent 执行：

| 强相关信号 | 示例 |
|-----------|------|
| 改/建同一个文件 | "创建 UserService 类"和"在其中添加 CRUD 方法" → 同一组 |
| 前后依赖（产出是输入） | "写 util 函数"然后"在同文件中调用它" → 同一组 |
| 共享内部状态 | "改构造函数私有字段"和"改引用该字段的方法" → 同一组 |
| 必须原子提交 | 拆开提交会导致中间状态编译/运行出错 → 同一组 |

#### 第二步：识别弱相关任务（应拆为不同组）

以下情况说明两个任务**弱相关**，可以拆到不同分支并行：

| 弱相关信号 | 示例 |
|-----------|------|
| 创建/改动不同文件 | 模块 A 的实现 vs 模块 B 的实现 → 不同组 |
| 仅通过接口/签名关联 | A 导出函数，B 调用该函数，各自内部逻辑独立 → 不同组 |
| 可独立验证 | 每组的产出可以单独 review 而不需要看另一组的代码 → 不同组 |
| 属于不同层级 | 数据层 vs UI 层 vs 配置层 → 不同组 |

#### 第三步：三问检验拆分结果

```
检验问 1: 两个 Agent 能否同时开始、互不等待？     → 不能 → 合并为一组或显式标注依赖顺序
检验问 2: 同一个文件是否只有一个 Agent 改？       → 多人改同一文件 → 必须合并为一组
检验问 3: 每个分支的产出能否独立 review？         → 不能单独审查 → 耦合太强，重新划分
```

#### 拆分示例

**重构场景** — 涉及 4 个改动：

| 改动 | 文件 | 依赖 |
|------|------|------|
| A. 删除旧方法 | api.js | 无 |
| B. 新增替代方法 | api.js | 依赖 A |
| C. 调用方适配 | service.js | 依赖 B 的函数签名（不依赖内部实现） |
| D. 配置文件更新 | config.js | 无 |

→ **分支 1**（api.js 组）：A + B，强相关，改同一文件
→ **分支 2**（service.js 组）：C，接口隔离，可并行
→ **分支 3**（config.js 组）：D，完全独立

**从 0 到 1 场景** — 搭建一个 Web 应用：

| 模块 | 文件 | 依赖 |
|------|------|------|
| A. 数据模型 + ORM | models/*.js | 无 |
| B. API 路由层 | routes/*.js | 依赖 A 的模型接口 |
| C. 前端页面 | pages/*.js | 依赖 B 的 API 接口 |
| D. 配置 + 部署 | config/, docker/ | 无 |

→ **分支 1**（数据层）：A — 其他模块的基础
→ **分支 2**（API 层）：B — 依赖分支1的模型签名，但内部独立
→ **分支 3**（前端层）：C — 依赖分支2的 API 签名，但内部独立
→ **分支 4**（基建层）：D — 完全独立，可与 1/2/3 并行

> ⚠️ 当存在依赖链（1→2→3）时，需在总计划中标注依赖顺序。并行度取决于最长依赖链。
> 如果**公共模块**（如 shared/、types/）被多个分支依赖，应在阶段三开始前先完成，或由协调者单独处理。

### 每个分支要做的

1. 创建 git 分支：`feature/描述性名称`
2. 创建任务清单文档：`docs/branch{N}-xxx-tasks.md`

### 关键设计

| 设计点 | 为什么 |
|--------|--------|
| 重构用 diff 格式展示变更 | Agent 不需要猜"改成什么样" |
| 新建用接口签名约定 | Agent 知道"要暴露什么"，内部自由发挥 |
| 行号定位（重构） | Agent 不需要搜索"在哪改" |
| Review 清单附在任务清单底部 | Codex 审查时一份文档搞定 |
| 完成标准可验证 | "搜索不到 xxx""文件存在且导出 yyy" 比 "确保完成" 明确 |

## 阶段三：并行执行

### 隔离方式：Git Worktree

```bash
# 每个分支一个独立工作目录
git worktree add ../项目名-分支1 feature/branch-1
git worktree add ../项目名-分支2 feature/branch-2
```

**为什么不用分支切换**：多 Agent 在同一目录切分支 = 竞态冲突。Worktree = 物理隔离，零冲突。

### 依赖链处理

当分支间存在依赖（如"分支2依赖分支1的接口"）时：

- **方案 A：接口先行** — 在阶段二先把接口定义（类型/签名）写入公共文件，各分支基于接口并行开发
- **方案 B：顺序执行** — 分支1先完成 → 分支2从分支1检出 → 分支3从分支2检出
- **方案 C：混合** — 无依赖的分支并行，有依赖链的串行

在总计划中用依赖图标注：
```
分支1（数据层）──→ 分支2（API层）──→ 分支3（前端层）
                                    ↗
分支4（基建层）──────────────────────    ← 与所有分支并行
```

### 每个 Agent 的执行流程

```
1. 进入自己的 worktree 目录
2. 读取 docs/branchN-xxx-tasks.md
3. 严格按 Task N.1 → N.2 → ... 顺序执行
4. 只操作任务清单指定的文件
5. git add 改动文件 && git commit -m "feat/refactor: 描述"
6. 报告 commit hash
```

### 全局规则（贴在提示词最前面）

```
1. 禁止操作 main 分支：不得 checkout main、不得 merge 到 main
2. 禁止 push：所有操作仅限本地
3. 禁止跨目录操作：每个 Agent 只在自己的工作目录内操作
4. 禁止操作范围外的文件：只创建/修改任务清单指定的文件
5. 所有新分支从指定的基础分支检出（见任务清单头部"基于"字段）
6. commit 信息使用约定前缀（feat: / refactor: / fix: / merge:）
```

**为什么用"禁止"而非"请注意"**：Agent 对禁止的遵守度远高于建议。要穷举具体行为，不留解释空间。

## 阶段四：逐分支 Codex 审查

### 流程

```
对每个 feature 分支：

  Codex 审查 → 通过？── 是 → 该分支完成 ✅
                │
                否
                ↓
         生成 docs/fix-plan-branchN.md
                ↓
         创建 fix/branchN-review-fixes 分支
                ↓
         按 fix-plan 修复 → commit
                ↓
         再次交给 Codex 审查 → 循环直到通过
```

### 审查命令模板

```
codex review @项目路径/xxx.js "对照 docs/branchN-xxx-tasks.md 的 Review 检查清单，逐项验证"
```

### 产出模板：fix-plan.md

```markdown
# 分支 N 审查修复计划

## 审查结果
- ✅ 通过项: ...
- ❌ 未通过项:

## 问题 1：问题标题
- **位置**：文件:行号
- **现状**：当前代码是什么样
- **期望**：应该是什么样
- **修复方式**：具体怎么改
```

### 修复分支命名规范

```
fix/branch1-review-fixes    ← 分支1的审查修复
fix/branch2-review-fixes    ← 分支2的审查修复
```

## 阶段五：合并 + 集成审查

### 步骤 A：创建合并分支

```bash
git checkout feature/branch-1
git checkout -b integrate/项目名

git merge feature/branch-2 --no-ff -m "merge: 合入分支2"
# 如有修复分支，也合入
git merge fix/branch1-review-fixes --no-ff -m "merge: 合入分支1审查修复"
```

### 步骤 B：集成审查（Codex）

```
codex review @xxx.js @yyy.js "对照 docs/integrate-review-tasks.md 审查合并结果"
```

### 步骤 C：集成修复（如需）

```bash
git checkout integrate/项目名
git checkout -b fix/integrate-review-fixes
# 修复 → commit → 再次 Codex 审查 → 通过后合回
git checkout integrate/项目名
git merge fix/integrate-review-fixes --no-ff -m "merge: 合入集成审查修复"
```

```
main ──────────────────────────────────────── (始终不动)
  │
  ├── feature/branch-1         ← Agent 1
  │     └── fix/branch1-fixes  ← 审查修复（如需）
  │
  ├── feature/branch-2         ← Agent 2
  │     └── fix/branch2-fixes  ← 审查修复（如需）
  │
  ├── feature/branch-N         ← Agent N
  │     └── fix/branchN-fixes
  │
  └── integrate/项目名          ← 合并所有 feature + fix
        └── fix/integrate-fixes ← 集成审查修复（如需）
```

## 文档体系

```
docs/
├── 总计划.md                    ← 阶段一：全局视角
├── branch1-xxx-tasks.md         ← 阶段二：Agent 1 施工图 + Review 清单
├── branch2-yyy-tasks.md         ← 阶段二：Agent 2 施工图 + Review 清单
├── integrate-review-tasks.md    ← 阶段二：合并后审查基准
├── fix-plan-branch1.md          ← 阶段四：Codex 审查问题（如需）
└── fix-plan-integrate.md        ← 阶段五（如需）
```

| 文档 | 谁写 | 谁读 |
|------|------|------|
| 总计划.md | 人 | 人（全局把控） |
| branchN-tasks.md | 人/AI | Agent（执行）+ Codex（审查） |
| integrate-review-tasks.md | 人/AI | Codex（集成审查） |
| fix-plan-xxx.md | Codex | Agent（修复） |

## 五条核心原则

1. **决策前置，执行分离** — 人做判断，Agent 做执行，两者不混
2. **一份文档两个用途** — 任务清单.md 既是施工图纸，也是审查基准
3. **物理隔离消除冲突** — 一个 Agent 一个 worktree，零冲突
4. **审查和修复分离** — Codex 输出 fix-plan.md，Agent 在 fix/ 分支修复，可追踪可回滚
5. **穷举式禁令** — 列出禁止的具体行为，不留解释空间

---

## 两轮 Codex 审查的区别

| | 逐分支审查（阶段四） | 集成审查（阶段五） |
|---|---|---|
| 审查对象 | 单分支文件 | 所有分支文件 |
| 对照文档 | branchN-tasks.md 底部 Review 清单 | integrate-review-tasks.md |
| 重点 | 功能正确、接口一致、模块边界 | 跨文件兼容、全局一致性、端到端验证 |
| 修复分支 | fix/branchN-review-fixes | fix/integrate-review-fixes |

---

## 适用边界

**✅ 适合**：
- 任何涉及多文件的开发任务（新建或修改）
- 模块间通过接口通信、内部逻辑独立
- 有可验证的完成标准
- 需要代码质量保证

**❌ 不适合**：
- 探索性开发（需求不明确，边做边想）
- 高度耦合（多人必须改同一个文件的同一段代码）
- 纯运行时验证（Agent 无法启动完整应用）
- 单文件简单修复（杀鸡不用牛刀）

## 13 步快速上手清单

```
□ 1.  理解需求，分析现状（读代码 / 设计架构）
□ 2.  做技术决策，写进总计划.md
□ 3.  按强相关性合并、弱相关性拆分，分 N 组任务
```
