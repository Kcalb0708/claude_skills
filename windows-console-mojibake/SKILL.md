# Windows 控制台中文乱码排查与修复

## 第一步:判断是显示乱码,还是数据真的坏了

乱码几乎总是"显示层"问题,原始数据(文件、JSON、数据库字段)本身是好的。动手改任何东西之前,先直接读一遍原始数据来源(用 Read 工具读文件,或 grep 数据源),确认里面的中文是不是正常的。如果原始数据本身存的就是乱码,那是写入时编码错了,是另一个问题,不适用本 skill。

典型案例:Claude Code 的任务标题在 `.claude/tasks/<sessionId>/<id>.json` 里存的是正常 UTF-8 "阶梯8a:提交预检 → 11项检查 → 生成审批卡片",但终端里的 Agent 失败通知显示成 "闃舵??8a锛氭彁浜ら?勬?? 鈫? 11椤规??鏌? 鈫? 鐢熸垚瀹℃壒鍗＄墖" —— 这就是纯显示层乱码,源文件完全没问题。

## 根因

Windows 控制台有两个独立、但经常一起出问题的代码页设置:

- **系统默认 ANSI 代码页(ACP)**:`HKLM\SYSTEM\CurrentControlSet\Control\Nls\CodePage` 下的 `ACP` 值。中文 Windows 通常是 `936`(GBK/简体中文),而不是 UTF-8 的 `65001`。这个值决定 cmd.exe、reg.exe 这类"非 Unicode 感知"的原生程序用什么编码往控制台写字符。
- **当前控制台活动代码页**:用 `chcp`(不带参数)查看,同样常见是 `936`。

只要这两个值不是 `65001`,就会出现乱码,而且方向不同、乱码长相也不同,可以反过来用长相判断方向:

1. **UTF-8 数据被当成 GBK 解码** → 变成"看起来像中文但完全不对"的字符(`阶梯` 变成 `闃舵`,箭头 `→` 变成 `鈫?`)。Claude Code 自己生成的 UTF-8 文本(任务标题、Agent 通知)经过 936 代码页的控制台渲染时就是这种乱码。
2. **GBK 数据被当成 UTF-8 解码** → 字节序列不合法 UTF-8,变成大量替换符 `�` 或 `锟斤拷`。cmd.exe/reg.exe 等原生程序自己输出的中文提示语(比如 `chcp`、`reg query` 的报错文本)被 UTF-8 终端读取时就是这种乱码。

两种乱码本质是同一个根因(代码页不是 65001),方向相反而已。

## 诊断命令

在 Git Bash 里查代码页/注册表时**必须**加 `MSYS_NO_PATHCONV=1`,否则 MSYS 会把 `/v`、`/t` 这类看起来像路径的参数自动转成 Windows 路径,导致 `reg` 报"无效语法"(这个报错本身还会显示成乱码,容易被误认成另一个问题,浪费时间排查错方向)。

```bash
# 查系统默认 ANSI 代码页
MSYS_NO_PATHCONV=1 reg query "HKLM\SYSTEM\CurrentControlSet\Control\Nls\CodePage" /v ACP

# 查当前用户新终端的默认代码页(不存在就是继承系统默认)
MSYS_NO_PATHCONV=1 reg query "HKCU\Console" /v CodePage

# 查当前控制台的活动代码页
MSYS_NO_PATHCONV=1 cmd.exe /d /c chcp
```

`ACP` 或 `chcp` 只要不是 `65001`,基本可以确认就是这个问题。

## 已知陷阱:临时 chcp 没用

在 Claude Code 的 Bash 工具里执行 `chcp 65001` 看起来会成功(`cmd.exe /d /c "chcp 65001 && chcp"` 会回显两行 `Active code page: 65001`),但**这个改动只作用于那一次工具调用产生的子进程**,不会持久化——下一次 Bash 调用又会打回系统默认值。更重要的是,Bash 工具的子进程和用户实际用来跑 Claude Code 的那个终端窗口是两个不同的进程树,就算改动能持久化,也影响不到用户真正看到乱码的那个窗口。

**结论:不要指望靠 Bash 工具里跑 `chcp` 来解决用户终端的乱码。这只能用来验证代码页数值、验证修复方向是否正确,真正生效必须用下面的持久化方案。**

## 修复方案(按影响范围从小到大)

改动前如果影响范围不确定(尤其方案三需要重启且影响整台机器),应该让用户选,不要替用户决定——尤其是在看起来是共享/生产服务器的机器上(路径里有 `Administrator`、`D:\projects\...` 这类线索时更要谨慎)。

### 方案一:仅当前终端会话临时生效

让用户自己在要用的那个终端里手动执行:

```
chcp 65001
```

关掉窗口就失效,每次新开都要重新执行。零风险,适合"先验证一下能不能解决问题"。

### 方案二:当前用户注册表持久化(推荐默认选项)

```bash
MSYS_NO_PATHCONV=1 reg add "HKCU\Console" /v CodePage /t REG_DWORD /d 65001 /f
```

只影响这个 Windows 账号**之后新开的**控制台窗口的默认代码页,不改系统级 ACP,不需要重启,风险低、可逆(还原用 `reg delete "HKCU\Console" /v CodePage /f`)。

**改完必须提醒用户:完全关闭当前终端窗口、重新打开一个、重启 Claude Code,乱码才会消失——当前已经打开的窗口不会自动刷新代码页。**

### 方案三:系统级全局修复(需要用户明确同意,不要自己执行)

控制面板 → 区域 → 管理 → 更改系统区域设置 → 勾选"Beta: 使用 Unicode UTF-8 提供全球语言支持" → 重启整台机器。

等价于把 `HKLM\SYSTEM\CurrentControlSet\Control\Nls\CodePage` 下的 `ACP`/`OEMCP`/`MACCP` 都改成 `65001`。这是唯一能连原生非 Unicode 程序(不只是控制台显示)都彻底修好的方案,但:

- 需要重启,会中断这台机器上其他正在跑的东西。
- 影响这台机器上所有程序,如果还跑着依赖 GBK/936 行为的老软件,可能受影响。
- 只给用户提供步骤,不要直接改 `HKLM` 注册表替用户执行这一步。

## 修复后验证

```bash
MSYS_NO_PATHCONV=1 cmd.exe /d /c "echo 你好世界"
```

在**新开的**终端里这行应该正常显示中文,而不是乱码或问号。也可以让用户直接看一眼原来乱码的那条 Agent/任务通知是否恢复正常。
